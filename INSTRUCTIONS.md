# PodScript Development Guidelines for AI Assistants

This document provides instructions for developing and maintaining the PodScript project. Please adhere to these guidelines strictly.

## 1. Project Overview

PodScript is a lightweight Lua script for managing Podman pods and containers. It uses declarative Lua files (called "recipes") to define pod configurations.

**Core Principles:**
*   **Simplicity:** The project aims for simplicity and has no external dependencies.
*   **Declarative:** Pods and containers are defined in Lua recipe files.
*   **Modular Source:** The core application logic is split into multiple files within the `src/` directory.
*   **Single File Release:** The final application is bundled into a single `pods.lua` file for deployment.

## 2. Technical Specifications

*   **Language:** Lua 5.4
*   **Dependencies:** None. Do not add any external dependencies.

## 3. Codebase Architecture

The development takes place in the `src/` directory. These files are bundled into `pods.lua` using the build system.

### 3.1. Directory Structure

*   `src/`: Contains the modular source code.
    *   `header.lua`: License header and global variables.
    *   `helper_*.lua`: Specialized utility functions (Print, String, Table).
    *   `helper.lua`: General helper functions.
    *   `container.lua`: Container management logic.
    *   `pod.lua`: Pod management logic.
    *   `recipe.lua`: Recipe loading and validation.
    *   `config.lua`: Configuration management.
    *   `main.lua`: Entry point and argument parsing.
    *   `mode_help.lua`: Help text and documentation.
*   `test.lua`: The main entry point for the test runner.
*   `build.lua`: The build script that bundles `src/` into `pods.lua`.
*   `pods.lua`: **[GENERATED]** The single-file release version. **Do not edit this file directly.**
*   `config.lua` & `recipe.lua`: Canonical configuration templates for users.

### 3.2. Section Descriptions and Naming Conventions

Each module in `src/` corresponds to a section with specific function naming conventions.

| Section     | Purpose                                       | Function Prefix | File in `src/` |
|-------------|-----------------------------------------------|-----------------|----------------|
| **Print**   | Handles all output to the command line.       | `print_`        | `helper_print.lua` |
| **String**  | Provides utility functions for strings.       | `string__`      | `helper_string.lua` |
| **Table**   | Provides utility functions for Lua tables.    | `table__`       | `helper_table.lua` |
| **Helper**  | Contains general helper functions.            | (none)          | `helper.lua` |
| **Container**| Manages Podman container lifecycle commands.  | `container__`   | `container.lua` |
| **Pod**     | Manages Podman pod lifecycle commands.        | `pod__`         | `pod.lua` |
| **Recipe**  | Handles loading and processing of recipe files.| `recipe__`      | `recipe.lua` |
| **Config**  | Manages the main `config.lua` file.           | `config__`      | `config.lua` |
| **Main**    | Contains the main application entry point.    | `main__`        | `main.lua` |

## 4. Build System (`build.lua`)

The `build.lua` script concatenates files from `src/` into `pods.lua`. It uses special annotations to process the code.

### 4.1. Build Annotations

*   `---@build block:`: Marks the start of the code block to be included in the build. Code before this annotation (like `require` statements used for dev mode) is ignored.
*   `---@build global:`: Forces a function to be global in the release version. By default, functions are made `local` during the build unless they match certain patterns.
*   `---@build const:`: Marks a variable as a constant. It transforms `VERSION = "1.0.0"` into `local VERSION <const> = "1.0.0"`.

### 4.2. Adding New Source Files

1.  Create the file in `src/` with the `---@build block:` annotation.
2.  Add a `require` statement to the appropriate file (usually `src/main.lua` or where it's needed) for development mode.
3.  Add the filename (without extension) to the `files` table in `build.lua` in the correct dependency order.

## 5. Coding Style and Formatting

*   **Indentation:** Use 4 spaces for indentation, not tabs.
*   **Function Order**: Order functions alphabetically within their section/file where possible.
*   **Style Consistency:** Adhere strictly to the coding style in `src/`.
*   **Comments:** Use English for all comments and variable names.
*   **Naming Conventions:** Follow the prefix conventions in Section 3.2.

## 6. Project Constraints (Anti-Patterns)

*   **Do not edit `pods.lua` directly**: All changes must be made to files in the `src/` folder.
*   **Do not add external dependencies**: The project must remain zero-dependency.
*   **Avoid global variables**: Use local variables unless `---@build global:` is necessary.
*   **Initialize variables**: Avoid `nil` where a default value (empty string/table) is more appropriate.

## 7. Development & Verification Workflow

This is the mandatory workflow for all changes:

1.  **Modify Source**: Edit files in the `src/` directory.
2.  **Test (Dev Mode)**: Run `lua test.lua --dev` to verify changes using the source files.
    *   Example: `lua test.lua --dev MySpecificTest`
3.  **Build**: Run `lua build.lua` to generate the new `pods.lua`.
4.  **Test (Release Mode)**: Run `lua test.lua` to verify the generated release file.
    *   All tests must pass in both modes before completing a task.
5.  **Document**: Update `CHANGELOG.md` if the changes are user-facing.

## 8. Testing Framework

The testing framework captures output and compares it against expectations. Test suites are in the `tests/` directory. Refer to existing tests for the structure of `expectations` and `simulate` flags.
